# Журнал архитектурных решений

Формат: решение → почему → чем платим. Статус «Принято» — зафиксировано в CLAUDE.md или подтверждено владельцем;
«Предложено» — ждёт подтверждения, может измениться на своём этапе. Решения не переписываются задним числом:
если передумали — новая запись со ссылкой на старую.

---

## Архитектура и стек

### D-001. Monorepo на pnpm workspaces — Принято (2026-11-04)
**Почему:** web, api и contracts меняются вместе; один репозиторий даёт атомарные изменения контракта и общий CI. pnpm — строгая изоляция зависимостей (нельзя импортировать то, что не объявлено), экономия диска, нативные workspaces без Lerna/Nx.
**Цена:** нужен порядок сборки пакетов; для 3 пакетов хватает `pnpm -r`, оркестратор (Turbo/Nx) не берём, пока сборка не станет медленной.

### D-002. Общие контракты на Zod в `packages/contracts` — Принято
**Почему:** одна схема даёт и тип TS, и валидацию на клиенте (UX), и на сервере (безопасность). Расхождение фронта и бэка ловится на typecheck, а не в проде.
**Цена:** contracts не зависят ни от React, ни от Fastify — только Zod.

### D-003. Деньги — целые копейки — Принято
**Почему:** float не представляет 0,1 точно; суммы корзины и заказа должны сходиться до копейки. `integer` в PostgreSQL (до ~21 млн ₽ на значение) и `number` в JS (точен до 2^53) — без библиотек decimal.
**Цена:** форматирование в рубли — одна утилита на клиенте; в API и БД всегда копейки, поле называется `…Kopecks`.

### D-035. contracts — пакет на исходниках TS, без своей сборки — Принято (2026-11-04)
**Почему:** `exports` указывает на `src/index.ts`; Vite, Vitest и tsx читают TS напрямую, поэтому нет шага «сначала собери contracts» и рассинхрона между `src` и `dist`. Production-сборка api делается tsup, который вшивает contracts в бандл, остальные зависимости ставятся в образ через `pnpm deploy`.
**Цена:** contracts нельзя опубликовать как npm-пакет как есть — нам это и не нужно.

### D-036. Версии инструментов: Node 26 LTS, pnpm 11, TypeScript 6.0, ESLint 9 — Принято (2026-11-04)
**Почему:** Node 26 — текущая LTS. TypeScript 7 уже вышел, но typescript-eslint поддерживает только `<6.1`; ESLint 10 вышел, но eslint-plugin-jsx-a11y поддерживает только до 9. Обновляемся, когда плагины догонят — отдельным коммитом.
**Следствие:** pnpm 11 по умолчанию не запускает install-скрипты зависимостей; разрешённые перечислены в `allowBuilds` в `pnpm-workspace.yaml` (пока только esbuild).

### D-008. Fastify + fastify-type-provider-zod — Принято
**Почему:** Fastify быстрее Express, имеет систему плагинов и хуков (удобно для `requireAuth`, rate limit, helmet), а type provider связывает схемы contracts с типами `request`/`reply` без дублирования.
**Цена:** плагины Fastify инкапсулированы — декораторы регистрируются через `fastify-plugin`.

### D-009. Drizzle ORM, SQL-миграции в репозитории — Принято
**Почему:** схема в TS близка к SQL, без рантайм-магии и тяжёлого клиента (в отличие от Prisma); типы выводятся из схемы. Миграции генерируются drizzle-kit, коммитятся и не редактируются задним числом.
**Цена:** сложные запросы (фасеты каталога) пишем на SQL-билдере вручную.

### D-010. Упрощённый FSD на фронте — Принято
**Почему:** слои `app → pages → widgets → features → entities → shared` с импортами только вниз не дают коду сплестись. Слой появляется, когда в нём есть код.
**Цена:** правило импорта проверяется линтером, иначе деградирует.

### D-011. Серверное состояние — TanStack Query, UI-состояние — Zustand, фильтры — в URL — Принято
**Почему:** данные с сервера живут в кеше Query с инвалидацией; Zustand — только для UI (меню, шторки, гостевая корзина — D-015). Фильтры и сортировка каталога — в search params: ссылкой можно поделиться, «назад» работает, перезагрузка не теряет выбор.

### D-012. CSS Modules + CSS-переменные из tokens.css; брейкпоинты через postcss-custom-media — Принято
**Почему:** CSS Modules — изоляция без рантайма CSS-in-JS. Токены — CSS custom properties. Переменные нельзя использовать в `@media`, поэтому брейкпоинты объявляются как `@custom-media --md (min-width: 768px)` и раскрываются при сборке. Autoprefixer по browserslist.

### D-013. Поддержка Safari 14.1 / iOS 14.5 с первого дня — Принято
**Почему:** требование проекта; дешевле не использовать лишнее сразу, чем выпиливать потом. `browserslist` и `build.target = safari14`.
**Следствия:**
- `accent-color` (Safari 15.4) не работает → собственные checkbox/radio, хотя в макетах он есть.
- `:focus-visible` (Safari 15.4) → базовый `:focus` + переопределение в `:focus:not(:focus-visible)`; Safari 14 отбрасывает правило с непонятным селектором, и остаётся видимый `:focus`.
- `aspect-ratio` (Safari 15) → фолбэк через `padding-top`; `dvh/svh` → `position: fixed; top/bottom: 0` для шторок; `:has()`, container queries — не используем.
- flex `gap` поддержан с 14.1 — используем.
- WebP есть только на macOS 11+, AVIF нет → `<picture>` с JPEG-фолбэком.
- `structuredClone`, `Array.prototype.at` — запрещены линтером.

### D-014. Шрифты self-hosted через @fontsource, только cyrillic + latin — Принято
**Почему:** без запросов к Google Fonts (приватность, скорость); подмножества уменьшают вес в разы. `font-display: swap`, preload для начертаний первого экрана.
**Цена:** подключать конкретные файлы подмножеств, а не общий `index.css` пакета.

### D-037. Шрифты: свой fonts.css, только нужные начертания, ₽ из latin-ext — Принято (2026-11-04)
**Почему:** общие CSS @fontsource тянут все подмножества (vietnamese, greek…). Свой `fonts.css` объявляет 19 `@font-face` только для используемых начертаний, только woff2 и только cyrillic + latin; `unicode-range` гарантирует, что браузер скачает файл, лишь когда на странице есть его символы. Знак ₽ (U+20BD) лежит в latin-ext, поэтому у Manrope есть отдельный `@font-face` с `unicode-range: U+20BD` — цены набираются фирменным шрифтом.

### D-038. Stylelint следит за цветами, PostCSS — за брейкпоинтами — Принято (2026-11-04)
**Почему:** правило «никаких цветов вне токенов» проверяется автоматически: hex, rgb/hsl и именованные цвета запрещены во всех CSS, кроме `tokens.css`. Брейкпоинты — custom media из `media.css` (D-012), подмешиваются в каждый CSS-модуль плагином `@csstools/postcss-global-data`. Классы CSS Modules — в camelCase. Правило `no-descending-specificity` выключено: состояния компонентов пишутся в естественном порядке.

### D-039. Соглашения компонентов — Принято (2026-11-04)
- Компонент лежит в `shared/ui/<Name>/<Name>.tsx` рядом с `<Name>.module.css`, без barrel-файлов.
- Необязательные пропсы объявляются как `prop?: T | undefined` — так их можно пробрасывать дальше при `exactOptionalPropertyTypes`.
- Состояние, которое в CSS требовало бы `:has()` (выбранная радио-карточка), передаётся пропсом.
- Карточка товара — «карточка-ссылка»: ссылка-название растянута `::after` на всю карточку (зона нажатия больше 44px, одна ссылка в порядке Tab), кнопки лежат поверх.
- Поля контейнера: 16px до 768px и 40px от 768px; отдельного значения для планшета в макетах нет.
- Колонтитулы: одна полная шапка и один полный подвал на всех страницах — подпись «Полный подвал — как на главной» в макетах означает именно это.

### D-045. Соглашения базы данных — Принято (2026-11-06)
- PK — `uuid DEFAULT uuidv7()` (встроен в PostgreSQL 18, упорядочен по времени — индексы не фрагментируются); номер заказа для людей — отдельный `GENERATED ALWAYS AS IDENTITY`.
- Колонки в snake_case через `casing: 'snake_case'` Drizzle — в коде camelCase, в SQL snake_case без ручных имён.
- Email хранится в нижнем регистре и проверяется `CHECK (email = lower(email))` — уникальность без citext; нормализует Zod-схема `emailSchema`.
- Миграции генерирует drizzle-kit, они коммитятся и не правятся задним числом; Prettier их не трогает.
- Тесты БД — на настоящем PostgreSQL: каждый файл создаёт временную базу, применяет миграции и удаляет её. CHECK, внешние ключи и частичные индексы на моках не проверить.
- Тип снимка адреса в `orders.delivery_address` берётся из contracts — одна схема и для БД, и для API.
- Вариант товара не удаляется сидом, а выключается (`is_active = false`): на него могут ссылаться заказы и корзины.

### D-046. Цена в URL каталога — в рублях — Принято (2026-11-06)
`?priceMin=4000&priceMax=9000` читается человеком; сервер переводит в копейки умножением на 100 — целые числа, без float (D-003). Во всех ответах API деньги — копейки.

### D-047. Гостевой заказ передаёт позиции в запросе — Принято (2026-11-06)
Корзина гостя живёт в браузере (D-015), поэтому `POST /orders` принимает `items` (только вариант и количество) для гостя; у вошедшего сервер берёт свою корзину. Цены сервер в любом случае считает сам.

### D-048. Длительности слоёв пирамиды — время затихания слоя — Принято (2026-11-06)
`top_minutes`, `heart_minutes`, `base_minutes` — момент, когда слой перестаёт звучать (15 мин → 3 ч → 8 ч), как шкала в product.html. Толщина слоя считается по длительности его звучания (разности) в сжатой шкале (степень 0,4), чтобы 15 минут и 5 часов оба оставались читаемыми.

### D-049. Действия карточки и товара до появления корзины — Принято (2026-11-06)
До этапа 6 «+» в карточке ведёт на страницу товара, «Сообщить» — к форме на странице товара (`#notify`), а «В корзину» и «В избранное» на странице товара видны, но неактивны с подсказкой. Окно выбора объёма появится вместе с корзиной — без неё оно было бы с неработающей кнопкой.

### D-050. Повтор запросов на клиенте — только при сетевых сбоях — Принято (2026-11-06)
TanStack Query не повторяет ответы 4xx: 404 и ошибка валидации не исправятся повтором, а пользователь лишние секунды смотрел бы на скелетон. Сетевые ошибки и 5xx повторяются до двух раз.

### D-051. Поиск — параметр каталога, а не отдельный эндпоинт — Принято (2026-11-06)
`q` входит в `catalogQuerySchema`: быстрый поиск в шапке и страница результатов — один и тот же `GET /api/products`, поиск можно сочетать с фильтрами и делиться ссылкой. ILIKE по названию, материалу и нотам и точное совпадение номера образца — на 16 товаров полнотекстовый индекс избыточен.

### D-052. Подзапросы в SELECT — только при запросе с JOIN — Принято (2026-11-06)
В запросе по одной таблице Drizzle пишет колонки в списке полей без имени таблицы, и коррелированный подзапрос `EXISTS (… WHERE variant.product_id = product.id)` сравнивает не те колонки. Такие условия ставим в WHERE (там имена полные) или выносим в отдельный запрос; тесты каталога проверяют счётчики, чтобы ловить эту ошибку.

### D-053. Сессии: устройство и сроки — Принято (2026-11-07)
- Токен — 32 случайных байта в httpOnly-cookie `nisha_session`, SameSite=Lax; в `sessions.id` — SHA-256 токена.
- Secure-флаг — `COOKIE_SECURE`, по умолчанию только в production: Safari не принимает Secure-cookie на `http://localhost`.
- Срок 30 дней, продление раз в сутки при обращении (не пишем в БД на каждый запрос); истёкшая удаляется при обращении.
- При входе и регистрации прежняя сессия удаляется (ротация против фиксации).
- Вход отвечает одинаково и за одинаковое время на неизвестный email и неверный пароль: argon2 проверяет «пустой» хеш.
- `next` после входа принимается, только если это путь нашего сайта (не `//…`, не `/\…`) — без открытого редиректа.

### D-054. CSRF — свой плагин на cookie, а не @fastify/csrf-protection — Принято (2026-11-07)
`@fastify/csrf-protection` хранит секрет в серверной сессии, а изменяющие запросы бывают и у гостя («Сообщить о поступлении», позже — гостевой заказ). Double-submit на отдельной cookie работает для всех; Origin проверяется, если браузер его прислал. В e2e API запускается с `WEB_ORIGIN` адреса vite preview.

### D-018. Единый формат ошибок API с кодами из contracts — Принято
**Почему:** `{ error: { code, message, details? } }`, где `code` — enum в contracts (`VALIDATION_FAILED`, `OUT_OF_STOCK`, `UNAUTHORIZED`…). Клиент ветвится по коду, а не по тексту; один обработчик ошибок в Fastify, без пустых catch.

### D-019. Типографика: статика вручную, текст из БД — через typograph.ts — Принято
**Почему:** статичный текст проверяется на ревью; контент из БД вводят люди в админке, поэтому неразрывные пробелы расставляются при выводе одной утилитой.

## Безопасность

### D-004. Серверные сессии в httpOnly-cookie, а не JWT — Принято
**Почему:** сессию можно отозвать мгновенно (выход, смена пароля, бан) удалением строки в `sessions`; httpOnly недоступна JS, поэтому XSS не украдёт токен. JWT в localStorage уязвим к XSS, а отзыв JWT требует чёрных списков — то есть той же таблицы.
**Цена:** запрос в БД на каждый аутентифицированный запрос (дёшево по индексу); нужна CSRF-защита (D-006). SameSite=Lax + Secure, ротация id при входе против фиксации сессии.

### D-005. Пароли — argon2id — Принято
**Почему:** победитель Password Hashing Competition, устойчив к GPU/ASIC за счёт памяти; рекомендация OWASP. Параметры хранятся в хеше, поэтому меняются без миграции.
**Цена:** нативная зависимость (`argon2`) — сборка в Docker на том же образе, что и рантайм.

### D-006. CSRF: double-submit токен + проверка Origin — Принято, реализовано в этапе 5 (свой плагин, `GET /api/auth/csrf`)
**Почему:** SameSite=Lax закрывает большинство межсайтовых POST, но не все сценарии. Токен в cookie (не httpOnly) + заголовок `X-CSRF-Token` на всех изменяющих запросах, плюс сверка `Origin` со своим доменом. Работает и без входа (гостевое оформление, подписка «Сообщить»).
**Цена:** клиентская обёртка над fetch обязана добавлять заголовок.

## Продукт: каталог

### D-025. Цена «от», фильтры и выбор объёма из карточки — Принято (2026-11-04)
- Цена зависит от объёма; «от [ЦЕНА]» — минимальная цена среди вариантов товара.
- Фильтры объёма и цены применяются к одному варианту: товар найден, если у него есть вариант нужного объёма в нужном диапазоне цены.
- Кнопка «+» в карточке не кладёт товар сразу, а открывает выбор объёма (поповер на десктопе, шторка на мобильном).
- Бейджи «Бестселлер», «Новый образец» и порог «Осталось N» задаются вручную в админке.

### D-026. «Из той же породы» — Предложено
**Правило:** до 4 опубликованных товаров: сначала того же материала, затем той же плотности, затем той же категории; текущий товар и товары без остатка — в конце.
**Почему:** название блока обещает родство по материалу, но материалов мало, и блок не должен пустеть.

### D-027. «Подбор аромата» — короткий опросник поверх фильтров каталога — Предложено
**Почему:** 3–4 вопроса (настроение → материал, интенсивность → плотность, для кого → категория) превращаются в обычные фильтры каталога; отдельная логика рекомендаций не нужна (правило 1 CLAUDE.md).

### Прочее по каталогу — Принято (2026-11-04)
- Товар может быть в нескольких категориях; «Подарочные наборы» и «Пробники» — обычные категории каталога.
- Товары «Для дома» имеют те же атрибуты (материал, ноты, объём).
- Коллекция — отдельная сущность. У каждого товара свои длительности слоёв пирамиды; срез на главной показывает бестселлер, отмеченный в админке.
- Первый экран главной — карусель из 3 слайдов; содержание слайдов 02–03 придумываем в духе макета.
- В объёме: поиск, журнал, запись на консультацию, «Подбор аромата», статические страницы. Вне объёма: подписка на рассылку (форму из подвала убираем).

## Продукт: корзина, заказ, оплата

### D-015. Корзина и избранное гостя — Принято (2026-11-04), часть про избранное заменена D-040
Гостевая корзина хранится на клиенте (localStorage, только `variantId` + количество); суммы и доступность считает сервер по `POST /cart/quote`. При входе или гостевом оформлении позиции переносятся в серверную корзину аккаунта (слияние по правилу CLAUDE.md: количества суммируются и обрезаются остатком). Избранное — только для вошедших: клик по сердцу у гостя предлагает войти.
**Почему:** гостевое оформление (D-022) невозможно без корзины у гостя, а CLAUDE.md требует тестов слияния корзин; при этом серверные анонимные корзины не нужны.

### D-028. Счётчики корзины по одному правилу — Принято (2026-11-04)
Все количества и суммы считает сервер по одному правилу: позиция без остатка показывается с пометкой, но не входит ни в сумму, ни в «N образцов · M флаконов», ни в «Товары, N шт.», ни в бейдж шапки.

### D-029. «Сообщить о поступлении» — подписка на товар по email — Принято (2026-11-04)
Подписка на товар целиком (не на объём); доступна гостю по email. Уведомление уходит, когда у товара появляется остаток хотя бы у одного варианта; подписка закрывается после отправки.
Подтверждено 2026-11-06, хотя в задании этапов 3–4 подписка была на вариант: таблица `stock_notifications` хранит `product_id`, один активный запрос на пару (товар, email).

### D-022. Гостевое оформление создаёт гостевой аккаунт — Принято (механика — Предложено)
**Принято:** оформить заказ можно без регистрации, указав контакты; автоматически создаётся гостевой аккаунт, в котором видно заказ.
**Предложенная механика:**
- новый email → создаётся аккаунт без пароля (`is_guest`), гостю сразу выдаётся сессия на этом устройстве, приходит письмо со ссылкой «установить пароль» (одноразовый токен с ограниченным сроком); после установки пароля аккаунт становится обычным;
- email уже зарегистрирован → заказ привязывается к существующему аккаунту, но вход не выполняется (иначе любой, кто знает чужой email, получил бы доступ к кабинету); пользователь получает письмо и видит заказ после входа.

### D-016. Остаток списывается при создании заказа, неоплаченный заказ живёт 5 минут — Принято (2026-11-04)
**Почему:** у нишевого дома маленькие остатки — продать последний флакон двоим недопустимо. `SELECT … FOR UPDATE` по вариантам в транзакции создания заказа. Если оплата не прошла за 5 минут или отклонена — заказ отменяется, остаток возвращается (фоновая задача в api).
**Цена:** нужна периодическая задача и тест на гонку.

### D-017. Статусы заказа — конечный автомат на сервере — Принято (2026-11-04), уточнено D-043
Статусы: «Ожидает оплаты» → «Оплачен» → «Передан в доставку» / «Готов к выдаче» (самовывоз) → «Доставлен»; из «Ожидает оплаты» и «Оплачен» — «Отменён».
Форма метки: активные — заливка, «Доставлен» — рамка, «Отменён» — пунктир. Вкладка «Активные» — всё до «Доставлен»; «Завершённые» — «Доставлен» и «Отменён».
Каждая смена пишется в `order_status_history` — из неё даты на шкале статуса.

### D-030. Оформление — одна динамическая страница — Принято (2026-11-04)
Контакты, доставка и оплата на одной странице; индикатор 01–03 показывает заполненность блоков; при смене способа доставки или адреса итог пересчитывает сервер.

### D-031. Доставка — Принято (2026-11-04)
Курьер (срок 1–5 дней, без выбора временного слота; адрес — город, улица и дом, квартира, комментарий), пункт выдачи СДЭК со списком и картой, самовывоз из бутика бесплатно.
Пункты СДЭК — мок-провайдер (список пунктов из сидов, своя карта-заглушка). Настоящая интеграция СДЭК вне текущего объёма; провайдер спрятан за одним модулем api, чтобы её можно было подключить позже.

### D-043. Статус заказа и статус оплаты — отдельные поля — Принято (2026-11-06), уточняет D-017
`order_status`: pending, paid, shipped, ready_for_pickup, delivered, cancelled. `payment_status`: pending, succeeded, failed, refunded. Переходы заказа: pending → paid | cancelled; paid → shipped (курьер, пункт выдачи) | ready_for_pickup (бутик) | cancelled; shipped / ready_for_pickup → delivered. Оплату меняет провайдер (вебхук), статус заказа — сервер по автомату.
